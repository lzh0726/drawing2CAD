### 六个重复生成样本

原来这些样本均达到 2048 token 后输出不完整。本轮首次输出重新分词为 8485～10459 token，生成了 27～60 个草图片段，仍在表达式中途结束。第二次修复同样重复且语法不完整。未触及 16384 token 上限；结合每个样本约 21～22.5 分钟的两次请求耗时，符合两轮生成软时间上限导致截断的特征。

当前没有持久化模型的精确 finish reason 和逐次生成耗时，因此不能把时间截断当作已精确观测到的停止原因。可以确定的是：增加预算没有让这些样本形成完整可执行代码，重复生成问题仍在。

### 00540970：超时之外还有上游错误

两次完整执行均记录 CAD_timeout。逐步诊断还在第 6 行首次拉伸发现 IntersectingWires。这比单纯“布尔合并太慢”的定位更具体：输入到后续运算的几何已经无效，可能增加布尔运算困难；但本次未证明这就是超时的唯一原因。修复回答仍与初次回答完全相同。

## 能得出的结论

本轮加长输出预算和启用诊断反馈，没有提高该固定回归集上的实体生成率。自动诊断能识别错误，真实模型没有表现出修正这批错误的能力。

源码核对确认控制器把 previous_code 和 error 交给推理子进程，推理侧把它们加入 task_prompt；三条关键源码为 server/demand_model.py、server/inference_once.py、server/model.py。这排除了“源码完全没有传递反馈”的简单遗漏，但尚未进行真实修复输入 token 的逐条审计。

与固定“图纸→正确代码”SFT 的训练形式结合看，这些结果提示模型的错误反馈利用和代码修复能力不足。确定性解码也会稳定复现其偏好的答案，但更换采样并不能保证获得正确几何；不能只凭该现象断言根因已经唯一确定。

## 下一步建议

1. 在开发样本上审计实际修复提示词与 token，确认原图、错误代码和诊断没有被模板或截断遗漏；保存不含凭据的输入摘要。
2. 对重复草图片段做检测与提前结束，将其记录为重复生成失败；先减少无效等待，不继续盲目增加生成时限。
3. 在开发集比较更明确的修复提示、有限采样候选或独立修复模型。当前自动重试没有实测收益，不应宣称提高准确率。
4. 若继续训练，准备“图纸＋错误代码＋具体诊断→正确代码”的修复 SFT 数据，来自训练/开发零件而非这批测试答案，并保留独立测试集。

本轮这批样本已参与诊断与策略开发，成绩应称为固定回归集结果，不能用作独立泛化能力证明。本轮只测实体有效性，没有重新测形状 IoU 或尺寸符合率。
